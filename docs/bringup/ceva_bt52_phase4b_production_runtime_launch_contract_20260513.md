# CEVA BT5.2 Phase4-B Production Runtime Launch Contract

## 1. Status

Phase4-B has started by extracting the current debug-owned launch path into an explicit contract.

```text
P4B_RUNTIME_LAUNCH_CONTRACT=PASS
P4B_RUNTIME_LAUNCH_MANIFEST=PASS
P4B_OPENSBI_MANIFEST_INPUT=PASS
CURRENT_LAUNCH_MODE=dev-gdb
TARGET_PRODUCTION_OWNER=opensbi
```

This is not a production launch pass. It is the first contraction step that removes path duplication and makes the current loader owner explicit.

## 4. What Is Still Development-Only

The current contract still depends on GDB for payload restore and launch. Therefore it is still development-only for these reasons:

- external debugger still owns payload injection and final launch;
- Linux proof still depends on a live J-Link/GDB session;
- OpenSBI currently consumes the manifest-driven DTB handoff and payload layout inputs (`CEVA_RUNTIME_DTB_LOAD_ADDR -> FW_PAYLOAD_FDT_ADDR`, `CEVA_RUNTIME_OPENSBI_PAYLOAD_OFFSET -> FW_PAYLOAD_OFFSET`);
- no published boot owner exists yet for sidecar or vendor runtime launch beyond those OpenSBI build seams.

The new manifest is generated by `scripts/generate_ceva_runtime_launch_manifest.sh`, refreshed by `rebuild_payload.sh` before and after the OpenSBI rebuild, and validated by `scripts/check_ceva_phase4b_runtime_launch_contract.sh`.

## 5. Target Production Direction

The target contraction for P4-B is:
```text
debug owner:      GDB restore + monitor go
target owner:     OpenSBI or approved earlier bootloader
payload source:   frozen artifact paths from the launch contract
runtime source:   approved sidecar or vendor runtime image
fallback path:    keep run_phase2_ceva_bt_linux.sh as debug fallback until production pass
```

The important change is not the addresses but the owner. Two real owner-transition seams now exist: `rebuild_payload.sh` consumes the generated launch manifest and drives OpenSBI's `FW_PAYLOAD_FDT_ADDR` from `CEVA_RUNTIME_DTB_LOAD_ADDR`, and also drives `FW_PAYLOAD_OFFSET` from `CEVA_RUNTIME_OPENSBI_PAYLOAD_OFFSET` so Linux entry staging is no longer hardcoded in the OpenSBI build path. GDB is still the primary launch owner, but the OpenSBI build path is no longer fully hardcoded.

## 6. Immediate Next Step

P4-B should next extend manifest consumption beyond the DTB handoff and payload layout fields, and hand actual runtime launch ownership to OpenSBI or an equivalent earlier boot owner. The most direct next target is to let the boot owner consume manifest-defined sidecar or runtime staging metadata without changing the frozen artifact paths yet.
